## Problem Description

TOCTOU（Time Of Check to Time Of Use）竞态条件是一种经典的并发缺陷模式，发生在代码先检查某个共享资源的状态（如文件是否存在、缓存条目是否有效），然后基于该检查结果执行后续操作时。在检查与使用之间存在一个时间窗口，任何并发参与者（包括系统自身的后台逻辑，如缓存过期清理）都可能在此窗口内改变资源状态，导致后续操作失败。

此模式在文件系统缓存层、资源生命周期管理模块中尤为常见。典型代码形如 `if os.path.exists(path): open(path)` 或 `if resource.is_available(): resource.use()`。在单线程测试中一切正常，但在并发环境下会间歇性地抛出 `FileNotFoundError` 等异常，表现为不稳定测试（flaky test）或生产环境中的偶发崩溃。

## Root Cause Analysis

问题的根本原因在于**开发者持有单线程心智模型**：假设文件系统或共享资源的状态在连续两行代码之间是稳定不变的。然而在并发环境中，这一假设从根本上就是错误的。

check-then-act 模式将一个本应原子化的操作拆分为两个独立步骤：

1. **Check（检查）**：查询资源当前状态（如 `os.path.exists()`）
2. **Act（操作）**：基于检查结果执行动作（如 `open()`）

这两步之间存在不可消除的时间间隙。在此间隙中：
- 其他线程可能删除了文件
- 系统自身的过期清理逻辑可能回收了资源
- 外部进程可能修改或移除了目标

由于竞态窗口通常极短，该缺陷在低并发场景下几乎不可复现，但在高负载生产环境中会以间歇性异常的形式暴露，极难调试定位。

## Solution Strategy

### 识别信号
- 观测到的现象:
  - 间歇性 `FileNotFoundError`、`ResourceNotFoundError` 或等价的"资源未找到"异常
  - 仅在并发/高负载场景下出现的 flaky test
  - 异常堆栈指向一个紧跟在存在性检查之后的资源访问操作
  - 涉及缓存层、临时文件、共享文件系统等可变共享资源的模块

### 解决步骤
1. **审计 check-then-act 序列**：在涉及文件系统或共享可变资源的模块中，搜索所有 `if exists → use` 模式，包括 `os.path.exists()`、`os.path.isfile()`、自定义的 `is_available()` 等检查方法
2. **替换为 EAFP 模式**：将"先检查再操作"替换为"直接尝试操作，捕获失败异常"。例如，将 `if os.path.exists(path): return open(path).read()` 改为 `try: return open(path).read() except FileNotFoundError: return default`
3. **在异常处理器中返回合理的回退值**：根据业务语义确定缺失资源的处理方式——对于缓存层，将缺失视为缓存未命中（cache miss）；对于配置文件，返回默认配置；确保回退行为与原有检查失败时的分支逻辑一致
4. **扩展审计范围至同模块相关方法**：同一模块中若存在一处 TOCTOU，极大概率存在多处。逐一排查所有对共享可变资源的 check-then-act 访问
5. **验证自我引发的竞态**：确认修复不仅覆盖外部并发删除，还覆盖系统自身逻辑（如一个线程执行缓存过期清理，另一个线程正在读取同一缓存条目）引发的竞态

### Why This Works

EAFP（Easier to Ask Forgiveness than Permission）模式将检查与使用**原子化地合并为单一操作**：直接尝试使用资源，如果资源已不存在，则通过异常处理优雅降级。这从根本上消除了竞态窗口——不再存在"检查"与"使用"之间的时间间隙。

相比文件锁或其他同步机制，EAFP 模式：
- **更简单**：无需引入锁管理、死锁预防等复杂逻辑
- **更高效**：在资源通常存在的正常路径上没有额外开销（异常仅在资源缺失时抛出）
- **更符合语言惯例**：在 Python 等异常处理代价低廉的语言中，EAFP 是推荐的惯用模式

## Boundary Cases

- **自我引发的竞态（Self-inflicted race）**：系统自身的后台逻辑（如缓存过期清理线程）在另一个线程即将读取资源时删除了该资源。修复时不能仅考虑外部并发，还必须覆盖系统内部的并发路径
- **多步依赖链中的 TOCTOU**：如果操作不仅是简单的"检查-打开"，而是"检查-打开-读取-解析"的多步链条，需确保异常处理覆盖整个链条中任何一步可能的资源消失
- **异常类型的完整性**：不同操作系统或运行时可能抛出不同的异常类型（如 `FileNotFoundError`、`PermissionError`、`OSError` 的不同子类），需确保捕获的异常类型覆盖所有"资源已不存在"的情况，但不过度捕获无关异常
- **回退值的语义正确性**：缓存未命中的回退值必须与业务逻辑一致——例如返回 `None` 还是触发重新计算，需根据上下文确定，不能简单地静默吞掉异常
- **日志与可观测性**：在异常处理中应考虑是否需要记录日志。对于预期中的缓存未命中可以静默处理，但对于非预期的资源消失应记录警告，以便排查潜在的系统配置问题

## PR Examples

- **django__django-16379**：Django 文件缓存层中的 TOCTOU 竞态条件。缓存的 `has_key()` 检查文件存在后再打开读取，但缓存过期清理可能在检查与读取之间删除文件，导致并发环境下间歇性 `FileNotFoundError`。修复方案为将 check-then-act 替换为 EAFP 模式，直接尝试打开文件并捕获 `FileNotFoundError`，将其视为缓存未命中。
